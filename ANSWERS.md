## Section 1 incident investigation log

This is an ordered investigation plan for the supplied hypothetical incident. No production logs, deployment diff or traces were supplied. The reproduction establishes an N+1 category; it cannot prove the actual unseen deployment cause or reproduce the stated 30-second latency.

1. Establish scope and timing: compare request latency/error rates by order count, deployment version and database host. Check database connection saturation, lock waits and upstream timings before assuming Python CPU is responsible. Preserve one affected request trace and its deployment metadata. Roll back or cap the response if the mobile dashboard is broadly unavailable.
2. Compare SQL fingerprints and counts for a small and a large account with Silk. Repeated customer/product primary-key lookups and one order-line SELECT per order, growing linearly with orders, implicate lazy relation traversal. A few individually slow queries instead suggest a missing index or changed plan; use EXPLAIN against representative data and inspect row estimates, scans and waits. Do not run expensive EXPLAIN ANALYZE blindly on production writes.
3. Inspect serializer properties, model methods, default managers and queryset construction, including related-model changes in the deployment. A view can remain unchanged while a serializer adds `order.customer.name` or a line's product name, or a manager stops applying eager loading. Django caches a relation per model instance, not globally by foreign-key value; repeated customers across orders do not prevent N+1 access.
4. Reproduce the same response shape against seeded data. Here 300 orders each traverse one customer, one reverse line collection and three products: `1 + 300 + 300 + 900 = 1501` application queries. This is the constructed example, not an invented measurement of the incident. Genuine Silk output and regression assertions corroborate it locally.
5. Fix and compare identical payloads. `select_related("customer")` joins the single-valued foreign key in the order SELECT. `Prefetch("lines", queryset=OrderLine.objects.select_related("product"))` fetches all lines with one IN query joining product; Django attaches those instances to each order's reverse-relation cache. Serializer iteration uses `.all()` so it consumes the prefetched cache. A later `.filter()` would bypass it. Two queries remain; line cardinality does not multiply the order rows as an all-in-one reverse join would.
6. Regression-test query counts at 1, 50 and 300 orders, inspect plans and total memory for larger datasets, and stage rollout while monitoring SQL counts and latency. Foreign-key indexes already support the lookups; adding another index would not remove round trips. The demo caps results at 300 and is not a full pagination/authentication implementation.

## Section 3 Question A — Django Admin Performance

First, I would inspect SQL from the actual changelist, including `list_display` callables and model `__str__()` methods. A column that accesses `obj.customer.company.name` can execute related-object queries for every visible row. I would set `ModelAdmin.list_select_related = ("customer__company",)` for foreign keys and use `get_queryset()` with `prefetch_related()` for reverse or many-to-many collections. A callable using `obj.lines.count()` may need an annotated `Count` instead. I would verify query counts with representative data and avoid joining unrelated large text fields; `defer()` helps only when display code never reads the deferred value.

Second, I would separate pagination cost from row retrieval. Django admin's paginator normally issues COUNT queries, and the unfiltered result count can add another expensive scan. Set `show_full_result_count = False` to remove the extra total, reduce `list_per_page`, and inspect the remaining filtered count. That setting does not eliminate the paginator's own COUNT. If exact totals are unnecessary, override `get_paginator()` with a deliberately approximate or bounded implementation and communicate the resulting navigation limitations. For very deep browsing, a separate cursor-based operational view may fit better than modifying admin semantics extensively.

Third, I would inspect search, ordering and edit-form widgets. Broad `search_fields` often generates costly case-insensitive substring predicates; a primary-key index cannot accelerate arbitrary text matching. Restrict search to useful fields, use exact or prefix lookups where appropriate, or override `get_search_results()` for PostgreSQL full-text search with a matching GIN index. Match a composite index to common filtering and deterministic ordering, then confirm with EXPLAIN. For foreign-key forms, replace huge select lists with `autocomplete_fields` or `raw_id_fields`; configure the related admin's search carefully. These changes trade unrestricted searching, exact totals or convenience for bounded database and rendering work.

## Section 3 Question B — Pagination Trade-offs

Offset pagination maps directly to Django queryset slicing, such as `qs[9900:10000]`. It is easy to expose numbered pages and lets a user jump to an arbitrary position. However, the database usually walks past the offset rows before returning the requested batch, even with a useful ordering index. An exact total adds a separate COUNT cost. A 10,000-row endpoint may perform adequately initially, but deep offsets grow expensive as the table expands. I would measure representative queries rather than choose solely from today's row count.

For mobile infinite scroll, I would usually use cursor pagination with a stable, indexed ordering. For example, order by descending `created_at` and `id`, and encode both in an opaque, validated cursor. The next query applies the corresponding lexicographic less-than predicate and LIMIT. A composite index on those columns lets PostgreSQL seek near the last row instead of discarding every earlier page. Django REST Framework's `CursorPagination` is an available component, but its ordering assumptions and handling of nonunique positions need review; an explicit compound keyset implementation makes the tie-breaking rule clear.

Concurrent inserts before an offset can repeat previously seen rows; deletes can cause rows to be skipped. A cursor anchored to immutable sort keys avoids those position shifts, which improves a scrolling feed. It does not create a database snapshot: deletions, permission changes and updates to ordering values can still change what the client sees. Newer inserts normally appear on refresh rather than in the remaining traversal. I would freeze ordering fields and carry validated filters through every cursor request.

I would choose offset for small administrative lists, numbered navigation and genuine random-page requirements. I would choose cursors for growing activity feeds and sequential browsing. The sacrifice is straightforward arbitrary page access and usually exact totals; cursor integrity, filter compatibility and backward navigation also require explicit design.
