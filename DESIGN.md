# Section 2 queue architecture

## Choice and durable source of truth

Celery with Redis provides scheduling, process supervision and late acknowledgement. PostgreSQL owns `EmailJob`, its stable UUID, failure count, due time and lease token; `SendAttempt` uses the limiter slot UUID as its primary key and records uncertainty and `DeadLetter` stores terminal failures. Celery messages contain only the job UUID. `enqueue()` accepts a caller-supplied UUID for submission deduplication, rejects conflicting payload reuse, and can join the order's database transaction. An `on_commit(..., robust=True)` callback publishes after commit. A callback failure is logged while the pending row remains recoverable. This is a small database outbox, not a distributed transaction.

Beat invokes `recover()` every 30 seconds, selecting due pending or expired processing rows in batches of 2,000. The same command can run manually after an outage. It intentionally permits duplicate publication: conditional SQL UPDATE claims the row, and sent/dead rows cannot be reclaimed. The row lease is 45 seconds, greater than the HTTP adapter's normal connect/read timeout budget. A UUID ownership token fences stale database completion writes. External sends cannot be fenced locally, and process suspension can outlive a lease. Monitor queue age, expired leases, uncertain attempts, dead-letter counts, Redis memory and recovery task failures.

Celery adds a dependency and operational settings, but avoids implementing transport acknowledgement and scheduling. Django Q would fit a Django-only team and can use ORM infrastructure, but still needs custom global Redis limiting and careful crash/delivery semantics. It adds no clear benefit for this explicit Celery assessment. A custom Redis Streams consumer group could use XACK and XAUTOCLAIM with pending entry tracking; we would then own retry schedules, supervision, poison messages and reclaim correctness. A custom list with BRPOP alone would lose popped jobs after a crash. PostgreSQL SKIP LOCKED polling could simplify the durable queue at modest scale, but would not meet the required Celery/Redis implementation.

## Atomic rolling window

`acquire.lua` executes Redis TIME, ZREMRANGEBYSCORE, ZCARD and conditional ZADD atomically. No client clock, pipeline race, per-worker limiter or `time.sleep()` is involved. One sorted set serves the entire provider account. Active calls use score +infinity. `finish.lua` changes that slot to Redis completion time; completed calls remain counted for another full window. Denials return the earliest completed-slot expiry, or one window if all slots are active. Celery reschedules with countdown and small positive jitter; the durable `deferrals` counter changes without consuming the provider failure budget.

This is deliberately more conservative than a start-time-only sliding window. If a worker obtains a permit and is suspended before network IO, an expiring start-time reservation could disappear before the actual attempt. Here it remains counted. At every admission there are fewer than 200 active plus recently completed calls; every attempt that started within the previous 60 seconds is either active or completed less than 60 seconds ago and therefore still counted. Each admitted slot permits exactly one adapter invocation. This proves the start-window bound under a functioning single authoritative Redis clock and no lost limiter state. Throughput can be below 200/minute when provider calls are slow.

A fixed INCR/EXPIRE window can admit nearly 400 calls around a boundary. A replenishing token bucket permits bursts depending on capacity; DECR plus a TTL alone is not a rolling limit. The conservative sorted set fits the literal rolling-window requirement and exposes active calls for incident investigation. A single Redis key avoids cross-slot Lua issues, but is also a serialization point; 200/minute does not require sharding.

## Failure, retries and dead letters

Redis errors fail closed before the provider. The job returns to pending with a five-second infrastructure deferral and no provider failure increment. Transient HTTP timeouts, connection errors, 429 and 5xx responses retry with `min(300, 2**failures) + uniform(0,1)` seconds. Unknown adapter exceptions also use this bounded failure path. Permanent responses terminate immediately; five provider failures terminate exhausted jobs. Database updates and `DeadLetter` creation share a transaction. Retrying a terminal message is a no-op. There is deliberately no automatic dead-letter replay command; inspect the reason and resolve the underlying issue before creating a new explicitly authorized job.

A killed worker or Redis outage during `finish()` leaves an active slot indefinitely. This sacrifices availability to protect the limit: repeated crashes can exhaust all capacity. Do not blindly expire or delete active slots. Before clearing a stranded slot, terminate/fence the corresponding old workers and allow at least 60 seconds since the last possible provider attempt. Safest procedure is to stop all account senders, verify they cannot resume, wait a full window, reconcile uncertain provider results, and then clear the limiter key before restarting. There is no automatic reconciliation tool claiming to know an external outcome. Redis persistence, backups, noeviction and a single authoritative primary are necessary. Redis state loss, clock jumps, unsafe failover, manual key deletion, or external senders using the same account invalidate the strict bound; quiesce senders for a full window before recovery. AOF cannot provide a universal no-data-loss guarantee.

## SIGKILL and delivery limitations

`task_acks_late=True` postpones broker acknowledgement until task return. `task_reject_on_worker_lost=True` asks a surviving prefork parent to requeue after abrupt child death; late ack alone does not do that. Prefetch is one per process. Killing the whole worker also kills the parent; Redis transport normally restores unacknowledged messages after its 3,600-second visibility timeout. Broker, backend and app visibility settings agree. The SQL lease/recovery path usually republishes earlier, after lease expiry plus the next beat cycle, independent of broker restoration. Tasks scheduled far into the future could exceed visibility timeout; configured delays here stay below it. Redis transport acknowledgements are not a durable exactly-once delivery protocol.

SIGKILL before provider IO leaves a recoverable row; during or after IO it leaves an ambiguous external result. The stable job UUID is passed as Idempotency-Key by the HTTP adapter, but deduplication depends on the provider's scope and retention period. If it does not honor the key, replay can deliver duplicates. Even with token-fenced SQL completion, an old suspended worker and a reclaimed worker can both invoke the provider. Both attempts obtain separate globally counted slots. A database/broker/provider distributed exactly-once transaction is not implemented. Accepted means the adapter accepted the request, not that the recipient received the email.

## Validation and references

Unit tests cover state transitions, retry budgets, dead letters, duplicate terminal tasks, outbox recovery and rollback. Real Redis tests use concurrent callers. With `--postgres`, the standalone harness creates an isolated generated PostgreSQL verification database; without it, it uses temporary SQLite. It never clears the application database. The standalone 500-job harness launches two actual Celery worker processes and a replacement, kills one after entering the provider, checks all rolling start-time windows, and reconciles final job and attempt counts. Fast mode uses 20 attempts per one-second window; production mode independently uses 200/60 seconds. Both use simulated delivery, never external email.
